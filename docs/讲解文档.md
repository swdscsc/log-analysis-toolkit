## 一、这个工具到底解决什么问题

场景：凌晨两点告警响了，网站 5xx 飙升。你打开服务器，面对一个 20 万行的 `access.log`。

你需要回答四个问题，而这个工具就是按这四个问题设计的：

| 问题 | 对应指标 | 代码里的实现 |
| --- | --- | --- |
| 影响多大？ | 错误率、5xx 占比、QPS | `error_rate` / `s5xx_rate` / `avg_qps` |
| 是谁在访问？ | UV、TOP IP | `top_ip` |
| 锅在哪个接口？ | 错误最多的接口 | `worst_path` |
| 慢在哪里？ | 接口平均耗时、慢请求明细 | `slowest_path` / `slow` |

**这四个问题就是运维排查的标准链路**：先定级（影响面），再定人（流量来源），再定位（故障接口），最后定因（性能瓶颈）。面试时把这个逻辑讲出来，比背代码值钱。

## 二、整体设计

```
日志文件
   │
   ├─ iter_records()   流式逐行读取（生成器）
   │      └─ parse_line()  正则解析成 Record 结构体
   │
   ├─ analyze()        一次遍历算完所有指标  ← 核心
   │
   └─ 三种输出
         ├─ print_report()  控制台摘要
         ├─ write_csv()     明细 CSV
         └─ write_html()    自绘 SVG 报表
```

**为什么用生成器而不是 `readlines()`？**

```python
# 不好的写法：一次性把 500MB 日志读进内存
lines = f.readlines()

# 本项目写法：读一行处理一行，内存恒定
def iter_records(path):
    with open(path, ...) as f:
        for line in f:
            yield parse_line(line)
```

这是面试高频考点。生成器（generator）让内存占用与文件大小无关，这是处理大文件的基本功。

## 三、核心代码逐段讲解

### 1）正则解析：为什么这么写

```python
LOG_PATTERN = re.compile(
    r'^(?P<ip>\S+)\s+\S+\s+(?P<user>\S+)\s+\[(?P<time>[^\]]+)\]\s+'
    r'"(?P<method>[A-Z]+)\s+(?P<path>\S+)\s+(?P<proto>[^"]*)"\s+'
    r'(?P<status>\d{3})\s+(?P<size>\d+|-)'
    r'(?:\s+"(?P<referer>[^"]*)"\s+"(?P<ua>[^"]*)")?'
    r'(?:\s+(?P<rt>[\d.]+))?\s*$'
)
```

对应一条真实的 Nginx combined 日志：

```
112.94.130.156 - - [07/Oct/2026:00:00:00 +0800] "POST /api/cart/add HTTP/1.1" 200 3228 "-" "Mozilla/5.0..." 0.153
└──── ip ────┘      └────── time ────────┘     └method┘└──path──┘       └st┘└size┘              └─ ua ─┘ └rt┘
```

三个容易踩坑的点：

- **`(?:\s+...)?` 的问号**：末尾的 `request_time` 和 UA 都是**可选字段**。很多 Nginx 没配 `$request_time`，不能因为字段缺失就整行解析失败。
- **`(?P<size>\d+|-)`**：日志里字节数可能是 `-`（比如 304 响应），要单独处理，否则 `int("-")` 直接崩。
- **路径去查询串**：`m.group("path").split("?")[0]`。如果不做这步，`/api/user?id=1` 和 `?id=2` 会被当成两个接口，热点统计全散掉。

### 2）一次遍历算完所有指标

```python
for r in records:
    total += 1
    status_cnt[r.status] += 1
    ip_cnt[r.ip] += 1
    path_cnt[r.path] += 1
    minute_cnt[r.ts.replace(second=0)] += 1   # 精确到分钟 → 算峰值 QPS
    total_bytes += r.size
    if r.status >= 400:
        path_err[r.path] += 1                 # 错误接口榜
    if r.rt > 0:
        path_rt[r.path].append(r.rt)          # 各接口耗时样本
```

**为什么强调"一次遍历"？**
如果每个指标都单独遍历一遍文件，10 个指标就是 10 次磁盘 IO。一次遍历全部算完，IO 只有 1 次——这是处理大数据的常识，也是面试官会追问的点。

`Counter` 是 `collections` 里的计数器，`most_common(n)` 直接出 TOP N，比手写排序干净得多。

### 3）峰值 QPS 怎么算

```python
minute_cnt[r.ts.replace(second=0)] += 1     # 把秒归零，按分钟聚合
...
peak_minute, peak_qps = minute_cnt.most_common(1)[0]
```

QPS 是「每秒请求数」。做法是把时间戳归到分钟桶，取最大的那个桶，再除以 60。
**注意**：这里峰值 40 是「那一分钟的总请求数」，严格说平均到秒是 40/60。**面试时如果被追问，要能说出这个区别**——真实的瞬时峰值应该按秒聚合，按分钟聚合会平滑掉尖刺。这是一个已知的、可以主动提出的改进点（显得你真的懂，而不是抄的）。

### 4）手写 SVG 图表

```python
def _svg_bars(data, width=560, bar_h=18, gap=6, label_w=150):
    max_v = max(v for _, v in data) or 1
    for i, (label, v) in enumerate(data):
        w = int((width - label_w - 90) * v / max_v)   # 按最大值归一化算宽度
        parts.append(f'<rect x="{label_w}" y="{y}" width="{w}" height="{bar_h}" rx="3" fill="#42a5f5"/>')
```

没用 matplotlib，而是直接拼 SVG 字符串。原因写在 README 里：**零依赖**。
代价是图表比较朴素，好处是任何人 `git clone` 下来不用配环境就能出报告——这在运维场景里很实际，因为你经常要在没网的服务器上跑。

## 四、怎么跑起来

```bash
cd log-analysis-toolkit
python src/gen_sample_log.py --lines 20000 --out sample/access.log
python src/log_analyzer.py sample/access.log --top 10 --slow 1.0 --out-dir report
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `--top N` | TOP N 显示数量，默认 10 |
| `--slow 1.0` | 慢请求阈值（秒），默认 1.0 |
| `--out-dir` | 报表输出目录 |
| `--no-html` | 只要控制台输出时用 |

改一行日志试试容错：往 `sample/access.log` 里随便插一行乱码，工具会跳过它继续跑，不会崩——这是刻意设计的。

## 五、面试问答（必须能答）

**Q：为什么要自己写日志分析，不用 awk 或者 ELK？**
> awk 适合一行命令取单个指标，但这个工具要同时算十几个指标并出报表，写在 shell 里会失控。
> ELK（Elasticsearch+Logstash+Kibana）是生产级的完整方案，但重、要运维成本；这个工具是**轻量应急**用的——服务器上没装 ELK 时，一个 Python 文件就能立刻出结论。
> 如果数据量到了千万级/需要长期存储检索，就应该上 ELK 或 Loki，这是我理解的工具边界。

**Q：日志有 500MB，你的程序能跑吗？**
> 能。用了生成器流式读取，内存占用跟文件大小无关，恒定在几 MB。
> 但单进程解析 500MB 大概要几十秒，如果要求更快，可以：按行切分后多进程并行（`multiprocessing`），或者直接用 Go 重写解析器。

**Q：`--slow` 阈值为什么默认 1 秒？**
> 1 秒是用户体验的心理阈值（超过 1 秒用户会感到卡顿）。但实际应该按业务定：静态资源可以放宽到 500ms，支付接口可能 300ms 就要告警。所以做成了命令行参数而不是写死。

**Q：发现错误率飙升，你的排查思路是什么？**
> 1. 看状态码分布：5xx 多说明服务端问题，4xx 多可能是客户端或接口变更；
> 2. 看错误最多的接口，定位到具体服务；
> 3. 看 TOP IP，排除是不是被扫描或压测；
> 4. 看接口耗时，判断是超时还是逻辑报错；
> 5. 再结合时间点去查那个服务的变更记录和数据库慢查询日志。

**Q：这个工具有什么不足？**
> 三个：
> ① 峰值 QPS 按分钟聚合会平滑掉秒级尖刺，应该按秒聚合；
> ② 单文件单进程，大日志慢，没做并行；
> ③ 不支持 gzip 日志直接读取，生产环境日志通常都是压缩的。
> 这些我都写在 README 的后续计划里了。

## 六、你可以自己加的改进（挑一个做，面试有话说）

1. **按秒聚合算真实峰值 QPS**（改一行 `replace(second=0)` → 直接用秒级时间戳）
2. **支持 `.log.gz`**：`gzip.open(path, 'rt')` 替换 `open()`
3. **告警推送**：错误率超阈值时调用企业微信/钉钉 webhook
4. **多文件合并**：`argparse` 改成接受目录，遍历所有 `.log`
